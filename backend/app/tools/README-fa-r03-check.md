# FA-R03 · проверка месяца

CLI-инструмент для **локальной** проверки сверки 1С ↔ банк и точности набора правил
классификации. В CI не запускается: работает с реальными выгрузками клиента.

## Где лежат образцы

Только локально, вне git: `var/fa-r03-client-samples/` (см. `.gitignore`).

Ожидаемые файлы (имена — по префиксу, регистр не важен):

| Префикс | Что это | Формат |
|---------|---------|--------|
| `S1_…` | выписка по счёту 51 из 1С | `1CClientBankExchange`, обычно `cp1251` |
| `S2_…` | карточка счёта 51 | `.xls` |
| `S3_…` | оборотно-сальдовая ведомость | `.xls` |
| `S12_…` | ОСВ по счёту 57.03 (эквайринг) | `.xls` |

Если S12 или S3 нет — соответствующий раздел пропускается с пометкой.

## Запуск

```bash
cd backend
python -m app.tools.fa_r03_check ../var/fa-r03-client-samples --month 2026-09
```

Нужно dev-окружение (`uv sync --group dev`): для `.xls` требуется `xlrd`, он стоит
**только в dev-группе** и в production-образ не попадает.

## Как читать результат

Инструмент печатает семь разделов. Главное — строки «совпало / расхождение»
и точность в разделе 6.

### 1. S1 · выписка по счёту 51

Кодировка, число документов, суммы поступлений и списаний, число суточных секций,
остаток на начало и конец, число ошибок цепочки остатков.

- `ошибок цепочки остатков: 0` — остаток каждого дня совпадает с началом следующего.
- Ненулевое значение означает разрыв в выписке; цифры дальше сверять нельзя.

### 2. Сверка по счёту 51: S1 = S2 = S3

Сравниваются четыре величины (начало, дебет, кредит, конец) с допуском **0,00**.
Строка `итог S1 = S2 = S3: совпало` — банк, карточка и ОСВ согласованы.
При расхождении печатается таблица по каждому источнику.

### 3. Сопоставление S1 ↔ S2 по номеру документа

Номер документа из выписки ищется **внутри названия документа карточки**
(1С пишет «… по вх.д. 420283»).

- `номер документа 1С найден в названии S2` — сколько документов нашли ровно одного кандидата.
- `не найден` — номер не встретился или не совпала сумма.
- `неоднозначно` — несколько кандидатов, нужна ручная проверка.
- `документов из нескольких строк карточки` — один платёж разбит на несколько проводок.

### 4. Эквайринг по счёту 57.03

Валовая сумма и комиссия берутся из **назначений платежа** в S1, оборот — из S12.

- `дней с расхождением «валовая = оборот 57.03»: 0` — валовая по дням равна дневному обороту 57.03.
- `разница «валовая − комиссия» vs S2: 0.00` — нетто-поступление совпало с карточкой.
- `не разобрано назначений` — формат назначения не распознан; такие дни выпадают из сверки.

Разбор опирается на проверку «валовая − комиссия = фактически поступившая сумма»,
поэтому поддерживает разные форматы банков. Если число не разобрано — это видно,
а не молча пропущено.

### 5. Комиссии и эквайринг на счёте 91.02

Проверка: комиссии банка из карточки **плюс** комиссия эквайринга **равны** обороту
Дт 91.02 в ОСВ. `разница: 0.00` — сходится.

### 6. Точность набора правил v1 против эталона S2

Эталон — секция по корреспондирующему счёту в карточке 51 (например, поступление
с 62.02 → операционная деятельность). Правила берутся из каталога
`classification_packs/ru-bank-clientbank/1.0.0` и применяются **тем же матчером**,
что в продукте, в памяти, без БД.

- `точность по сумме` и `точность по количеству` — проценты совпадений.
- `матрица «эталон → правило»` — куда какие суммы разошлись, в рублях и штуках.
- `промахи` — до 20 строк с обобщённым шаблоном (цифры → `#`, без названий и ИНН).

**Важно:** выборка обучающая. 100 % на ней не доказывают качества на новых данных —
нужен hold-out (другой месяц или другой банк).

### 7. Ожидаемые образцы

S11 (журнал реализаций) и S9/S10 (счёт 62) пока не поставлялись. Разделы
помечены как «ожидается образец» и в проверку не входят.

## Что инструмент НЕ делает

- Не пишет в базу, не вызывает API, не трогает staging.
- Не печатает названия контрагентов, ФИО, номера счетов и тексты назначений:
  в выводе только числа, агрегаты и обобщённые шаблоны (цифры заменены на `#`).
- Не включает набор правил в продукт и не меняет настройки tenant.
