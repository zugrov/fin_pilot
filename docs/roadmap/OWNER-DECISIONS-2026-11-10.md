## 1. ADR-004 · банк и начисление (Q1–Q5)

### ADR-004 Q1 · Что главнее для денег и выручки в ближайшем продукте?

**Суть:** Нужно зафиксировать, откуда в первую очередь берутся цифры: из выписки банка, из учёта 1С или из двух параллельных «лент» без смешивания.

| Вариант | Смысл |
| --- | --- |
| **A** | Деньги и ОДДС — из **банка**; выручка и дебиторка v1 — из **начислений** (реестр/1С). |
| **B** | Всё важное — из **учёта 1С**; банк только для проверки. |
| **C** | В интерфейсе **две отчётные линии** (наличные деньги vs начисления), без одной «общей выручки». |
| **Гибрид** | Описать своими словами. |

| Вариант | Для пользователя | Для разработки |
| --- | --- | --- |
| A | Понятный ОДДС «как в банке»; выручка может отличаться по датам от поступлений. | Совпадает с FA-R06.1 и ClientBank; минимум переделки. |
| B | Цифры ближе к бухгалтерии, но импорт и сверки тяжелее. | Конфликт с текущим pipeline и REL1 **A**; большой объём FA-R03. |
| C | Честные подписи, меньше путаницы «почему не сходится». | Два режима в UI/API; больше work в FA-R07. |

**Рекомендация:** **A** — уже работает в D3 и FA-R06.1.  
**Блокирует:** FA-R06.2 отчёты, единый виджет «выручка» в FA-R07.  
**Обратимость:** **трудно** после публичных отчётов и обученных пользователей; на этапе design — **легко**.

### ADR-004 Q2 · Как строить первый управленческий ОПиУ (целевой D4)?

**Суть:** По каким статьям ОПиУ брать банк, по каким — начисление из учёта.

| Вариант | Смысл |
| --- | --- |
| **accrual-first** | Почти всё из ОСВ/журналов 1С. |
| **bank-first** | Операционные денежные статьи только из банка. |
| **mixed map** | **Таблица по статьям** (`bank` / `accrual` / `hybrid` / `unavailable`). |

| Вариант | Для пользователя | Для разработки |
| --- | --- | --- |
| accrual-first | Ближе к бухотчётности, слабая связь с кассой. | Много импортов 1С до «полноты». |
| bank-first | Хороший cash view, слабый затратный ОПиУ без учёта. | Узко для D4. |
| mixed map | Гибко по профилю организации (ADR-003). | Отдельный документ «карта статей»; умеренный объём. |

**Рекомендация:** **mixed map** (после Q1=A).  
**Блокирует:** FA-R06.2 объём P&L.  
**Обратимость:** **средняя** — карту можно дополнять без ломки закрытых периодов, если зафиксировать snapshot правил.

### ADR-004 Q3 · Как считать месяц «закрытым»?

**Суть:** Одна кнопка закрытия на всё или отдельно деньги и выручка.

| Вариант | Смысл |
| --- | --- |
| **single** | Один флаг `period closed` на месяц. |
| **dual** | Отдельно `cash_reconciled` и `revenue_reconciled`. |

| Вариант | Для пользователя | Для разработки |
| --- | --- | --- |
| single | Проще mental model. | Риск «закрыли» при несверенном cash или revenue. |
| dual | Видно, что именно готово. | Два статуса в FA-R06.4 и UI. |

**Рекомендация:** **dual** (согласуется с разными источниками Q1).  
**Блокирует:** FA-R06.4.  
**Обратимость:** **легко** на staging; **трудно** менять после реальных закрытых месяцев в prod.

### ADR-004 Q4 · Автоматически связывать поступление на счёт с продажей?

**Суть:** Может ли система сама ставить связь «оплата ↔ выручка» без действия сотрудника.

| Вариант | Смысл |
| --- | --- |
| **да с лимитами** | Авто-match при совпадении сумма/дата/контрагент, с потолком и audit. |
| **нет** | Только ручные и явные `revenue_cash_matches` (как v1). |

| Вариант | Для пользователя | Для разработки |
| --- | --- | --- |
| да | Меньше ручной работы, риск ошибочных связей. | FA-R03.3 lineage + правила + откат. |
| нет | Предсказуемость, больше ручного труда. | Меньше рисков на пилоте. |

**Рекомендация:** **нет** до стабильных S10/S11 и lineage.  
**Блокирует:** автоматизацию дебиторки.  
**Обратимость:** **легко** включить позже флагом.

### ADR-004 Q5 · Если банк и карточка 51 не сходятся после сверки?

**Суть:** Запрещать ли закрытие месяца или только показывать предупреждение.

| Вариант | Смысл |
| --- | --- |
| **block** | Нельзя закрыть период, пока есть расхождение. |
| **flag-only** | Можно работать, quality flag в отчётах. |

| Вариант | Для пользователя | Для разработки |
| --- | --- | --- |
| block | Жёсткий контроль. | Нужны пороги и UX «что исправить». |
| flag-only | Не блокирует пилот на неполных данных. | FA-R03.2 остаётся read-only контролем. |

**Рекомендация:** **flag-only** на staging и пилоте.  
**Блокирует:** жёсткий FA-R03.2 product gate.  
**Обратимость:** **легко** ужесточить позже.
