# ADR-004 · Приоритет источника: банк (деньги) vs начисление (учёт / реестры)

**Статус:** **proposed** — без кода, без миграций, без изменения продуктовых регистров.  
**Дата:** 2026-11-10.  
**Контекст решений:** D3 (ближайший объём: деньги, выручка, планы), D1/D2; `source_precedence_for_target_pnl_and_balance` — вариант **A** (деньги/ClientBank для текущей модели), **ADR по начислению обязателен** до FA-R06.1–06.4 и FA-R07 — **deferred** (REL1, 2026-10-27).

**Связанные документы:** [ADR-001](ADR-001-unified-ingestion.md) §6 (`claimed` / `reconciled`), [ADR-002](ADR-002-acquiring-revenue-from-bank-statement.md), [ADR-003](ADR-003-organization-profile-and-tax-rules.md), [FA-R06.1-management-rules-v1.md](FA-R06.1-management-rules-v1.md), [DECISIONS.md](DECISIONS.md) D3–D4.

---

## 1. Проблема

В управленческом продукте одновременно существуют:

- **Денежные факты** — преимущественно из **банковской выписки** (ClientBank, `CashTransaction`), с классификацией в ОДДС.
- **Начисленные факты** — **выручка** (`RevenueEntry` из реестров/1С), **дебиторка** (продажи − оплаты), в перспективе **ОСВ и карточки** как контроль и обогащение.
- **Планы и прогнозы** — отдельные источники без «закрытия месяца».

Нужно зафиксировать **какой источник первичен** для каких отчётов и статей, чтобы не дублировать обороты, не смешивать поступления с выручкой (finpilot rule) и не пересчитывать закрытые периоды без явной политики.

**Текущая практика (до ADR):** для **D3** деньги строятся из **банка**; выручка v1 — из **revenue register**; сверка bank ↔ card51 — read-only (FA-R03.2); эквайринг — нетто по выписке ([ADR-002](ADR-002-acquiring-revenue-from-bank-statement.md)). Полный ОПиУ и управленческий баланс — **целевой продукт** (D4), источник истины по статьям **TBD** (ADR-001 §8).

## 2. Ограничения и инварианты

| Инвариант | Источник |
| --- | --- |
| Поступление на счёт **≠** выручка (начисление) | finpilot rule, FA-R06.1 §2 |
| Денежный поток **≠** прибыль | finpilot rule |
| Суммы — **Decimal** / NUMERIC; нет данных → **unavailable**, не 0 | finpilot rule |
| `DatasetCoverage`: банк/1С = макс. **claimed** до сверки | ADR-001 |
| Закрытый период: без пересчёта при смене профиля | ADR-003 |
| Реальные ClientBank **не** в git/staging | DECISIONS 2026-10-27 |

## 3. Варианты

### Вариант A · «Банк первичен для денег, начисление — для выручки и дебиторки» (рабочая гипотеза D3)

| Область | Authoritative | Контроль / вторичный |
| --- | --- | --- |
| **ОДДС** (operating/investing/financing) | `CashTransaction` из **ClientBank** (+ классификация) | Карточка 51, ОСВ 51 — **сверка**, не подмена суммы |
| **Выручка v1** (snapshot, дебиторка aging) | **RevenueEntry** (реестр / импорт начислений) | Журнал реализаций S11, ОСВ 90 — сверка и coverage |
| **ОПиУ (целевой)** | **TBD по статьям**: выручка — начисление; часть статей — из ОСВ/реестров | Банк — для **денежных** статей и cash-to-accrual мостов |
| **Баланс (целевой)** | Смешанный: денежные остатки — банк+учёт; 62 — начисление+match | ОСВ 62 vs 62.01/62.02 — отдельные срезы (sample-matrix) |
| **Эквайринг** | Нетто **выписка** на 51 | 57.03 — эталон комиссии (ADR-002) |

**Плюсы:** совпадает с уже принятой FA-R06.1 v1 и импортом ClientBank; минимум двойного учёта в D3.  
**Минусы:** ОПиУ и баланс требуют **карты статей**; задержка cash vs accrual видна пользователю без явного моста.

### Вариант B · «Единый начисленный контур (1С/ОСВ) первичен, банк — сверка»

| Область | Authoritative | Банк |
| --- | --- | --- |
| ОДДС | Производные от **учётных** проводок (51, 50, 57…) | Выписка — контроль итогов и timing |
| Выручка | ОСВ 90 / журнал реализаций | Поступления 62↔51 — match |
| ОПиУ / баланс | ОСВ и регистры 1С | Вторично |

**Плюсы:** ближе к «бухгалтерии как истине» для полного контура.  
**Минусы:** дублирование с текущим pipeline ClientBank; риск **завышения** операционного ОДДС (gross/commission ADR-002); сильная зависимость от полноты и формата **всех** выгрузок 1С; противоречит **A** в DECISIONS без явного пересмотра владельцем.

### Вариант C · «Раздельные витрины: cash-отчёт и accrual-отчёт, без слияния в одну цифру»

- Две параллельные линии: **факт денег** (банк) и **факт начисления** (revenue/OSV).
- UI и API **никогда** не складывают их в одну «выручку» или «прибыль» без подписи режима.
- Согласование — только в **сверках** (FA-R03.2+, FA-R06.2) и quality flags.

**Плюсы:** честно для D3→D4; снимает часть конфликтов дедупликации.  
**Минусы:** сложнее UX; требует дисциплины в именовании и entitlement.

## 4. Последствия по областям

| Область | A (банк $ / начисление выручки) | B (учёт первичен) | C (две витрины) |
| --- | --- | --- | --- |
| **ОПиУ** | Cash costs — из банка позже (FA-R06.2+); revenue — начисление | Всё из ОСВ/регистров | Два отчёта; мост — справочно |
| **ОДДС** | Банк authoritative | Риск расхождения с импортом | Банковая витрина = A |
| **Баланс** | 51/деньги — банк+сверка; 62 — revenue+match | 62 из ОСВ | Раздельные срезы + сверка |
| **Дедупликация** | `external_id` на cash; отдельные identity для revenue | Один ключ на проводку 1С | Явное разделение по `entity_kind` |
| **Закрытие периода** | Cash closed ≠ revenue closed (разные coverage) | Одно закрытие по учёту | Два флага closed |
| **Миграция** | Минимальная: усилить lineage (FA-R03.3) | Пересмотр import_service, правил | Новые report modes / entitlements |

## 5. Рекомендация (агент, не решение владельца)

Для перехода **D3 → FA-R06.2–06.4** без ломки принятого:

1. **Зафиксировать вариант A** как **операционный default** для денег и **начисление** для `RevenueEntry` / дебиторки v1 — согласовано с FA-R06.1 и REL1 A.
2. **Не** объявлять банк authoritative для **начисленной выручки** и **не** объявлять журнал реализаций authoritative для **ОДДС**.
3. Подготовить **карту статей** для будущего ОПиУ (FA-R06.2+): по каждой статье — `bank | accrual | hybrid | unavailable` (**ADR-004 implementation map** — отдельный документ после принятия).
4. Для спорных кейсов (аванс, эквайринг, депозиты) — ссылаться на **ADR-002**, **ADR-003** и профиль `money_channels`.
