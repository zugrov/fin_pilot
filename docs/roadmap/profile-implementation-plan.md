# План реализации профиля организации (без кода и SQL)

**Статус:** черновик для обзора; к реализации после принятия [ADR-003](ADR-003-organization-profile-and-tax-rules.md).  
**Границы:** только описание объёма, пакетов, порядка и рисков; **без** фрагментов кода, **без** SQL и схем БД.

**Связь:** [ADR-003](ADR-003-organization-profile-and-tax-rules.md), [ADR-002](ADR-002-acquiring-revenue-from-bank-statement.md), [FA-R03.2](FA-R03.2-export-checklist-by-profile.md).

---

## 1. Цель

Ввести в продукт **версионируемый профиль организации** с журналом изменений, справочником норм и отражением в UI/API так, чтобы:

- флаги качества (`unavailable`) и разрезы (НДС, ОДДС, эквайринг) согласовывались с профилем;
- закрытые периоды не пересчитывались при смене правил;
- **персональный список выгрузок** и подсказки следовали источнику учёта и ролям.

---

## 2. Пакеты работ

| Пакет | Содержание (логика, не реализация) |
| --- | --- |
| **P1 · Модель и справочник** | Сущности профиля по ADR-003 (версии с `effective_from`); справочник норм с `source_url` / `verified_at`; валидация несовместимых сочетаний формы и режима; правило «налоговые поля — с первого числа месяца». |
| **P2 · API и аудит** | Чтение/запись версий профиля (роли owner/accountant); неизменяемость применённого снимка к закрытому периоду; запись в **существующий** механизм аудита (как в ADR-003, без нового дублирующего журнала). |
| **P3 · Мастер в интерфейсе** | Шаги регистрации по §6 ADR-003; баннеры при `unknown` / `unspecified`; отображение налоговых подсказок по матрице ролей (решение владельца §11 ADR-003). |
| **P4 · Качество расчётов и ОДДС** | Связка `vat_status`, `money_channels`, `revenue_recognition_method` с флагами качества и агрегатами ОДДС (§5 ADR-003); для эквайринга — приоритет ОСВ / выписка по [ADR-002](ADR-002-acquiring-revenue-from-bank-statement.md). |
| **P5 · Персональный список выгрузок** | Генерация и хранение чек-листа по [FA-R03.2](FA-R03.2-export-checklist-by-profile.md) при изменении `accounting_source`, формы, режима; синхронизация подсказок без подмены учёта. |

---

## 3. Порядок и зависимости

Рекомендуемая последовательность (каждый следующий пакет опирается на контракт предыдущего):

1. **P1** — модель и справочник (истина для остальных слоёв).
2. **P2** — API и аудит поверх P1.
3. **P3** — мастер; потребляет P2 и контракт полей P1.
4. **P4** — встраивание в расчёты и отчёты; зависит от P1–P2 и согласованных правил ADR-002/003.
5. **P5** — персональный список выгрузок после стабилизации полей профиля и импорта (FA-R03).

**Критический путь:** P1 → P2 → P4 (без рабочего API профиля нельзя корректно выставлять флаги в контуре расчётов).

---

## 4. Миграции данных (только описательно)

- Ввести хранение **версий профиля** с `effective_from` и ссылкой на организацию/арендатора.
- Ввести **версии справочника норм** с метаданными проверки; связь с периодами отчётности — по политике продукта (не смешивать с версией профиля без явного правила).
- Для существующих организаций: одна **начальная версия** профиля с консервативными `unknown` / `unspecified` и баннерами (как в ADR-003).
- Закрытые периоды: применяется **снимок профиля на дату закрытия**; миграции не пересчитывают агрегаты задним числом.

Детали полей и ограничений — в миграционной задаче после утверждения схемы владельцем.

---

## 5. Тесты (ожидаемый контур)

| Уровень | Фокус |
| --- | --- |
| **Контракт** | Валидность переходов `vat_status`, несовместимость режимов, дата `effective_from` для налоговых полей. |
| **API** | Права ролей, запрет изменения снимка для закрытого периода, append-only журнал аудита. |
| **Интеграционные (продукт)** | Снимки экранов при `vat_basis_unknown` vs «не применяется»; строки матрицы §7 ADR-003 (в т.ч. неподдерживаемые режимы — корректное сообщение пользователю). |
| **Регресс расчётов** | Флаги качества и ОДДС при смене профиля только для **открытых** периодов; сценарии без ПДн. |

Объём e2e минимизировать: покрывать сценарии, где меняется поведение пользователя или отчёта.

---

## 6. Ориентир по объёму

Черновая оценка (после уточнения минимума полей §11 ADR-003):

- **P1 + P2:** крупная часть работы (модель, миграции описательно, API, права).
- **P3:** средний объём (UX, локализация сообщений, баннеры).
- **P4:** высокая вариативность (сколько отчётов затронуто в первой волне).
- **P5:** средний объём при наличии стабильного FA-R03.2 и форматов импорта.

Точные спринты не фиксируются в этом документе.

---

## 7. Решения, которые должен принять владелец

См. §11 [ADR-003](ADR-003-organization-profile-and-tax-rules.md). Дополнительно для плана внедрения:

- **Минимум полей** первого релиза и обязательность мастера до доступа к отчётам.
- **Матрица видимости** налоговых подсказок (owner / accountant / viewer).
- **Приоритет облачных систем** после 1С (список вендоров и критерии экспорта).
- **Граница P4:** какие отчёты в первой волне переводятся на профиль, что остаётся `unavailable` до второй волны.
