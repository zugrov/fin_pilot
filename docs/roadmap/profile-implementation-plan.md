# План реализации профиля организации (без кода и SQL)

**Статус:** черновик для обзора; к реализации после принятия [ADR-003](ADR-003-organization-profile-and-tax-rules.md).  
**Границы:** только описание объёма, пакетов, порядка и рисков; **без** фрагментов кода, **без** SQL и схем БД.

**Связь:** [ADR-003](ADR-003-organization-profile-and-tax-rules.md), [ADR-002](ADR-002-acquiring-revenue-from-bank-statement.md), [FA-R03.2](FA-R03.2-export-checklist-by-profile.md).

---

## 1. Цель

Ввести в продукт **версионируемый профиль организации** с журналом изменений, справочником норм и отражением в UI/API так, чтобы:

- флаги качества (`unavailable`) и разрезы (НДС, ОДДС, эквайринг) согласовывались с профилем;
- закрытые периоды не пересчитывались при смене правил;
- **персональный список выгрузок** и подсказки следовали источнику учёта и ролям.

---

## 2. Защита текущего пилота

Пока профиль организации **не подтверждён** (нет явного подтверждения уполномоченной ролью записи):

- существующие **экраны и расчёты** ведут себя **как до внедрения профиля**;
- показывается **баннер** о необходимости заполнить/подтвердить профиль;
- ограничения **`unavailable`** по налогово-зависимым разрезам **не включаются** от недозаполненности профиля — только после **подтверждённого** профиля применяются правила ADR-003 к качеству таких разрезов.

**Тестовая организация владельца:** после готовности **P2** (чтение и запись профиля с аудитом) заполняет и подтверждает профиль **сразу**, чтобы приёмка и регресс шли на «боевой» ветке логики без задержки на UI-мастер.

## 3. Пакеты работ (дробление P1/P2)

### 3.1 Сводная таблица

| Пакет | Содержание (логика, не реализация) |
| --- | --- |
| **P1a · Справочник норм** | Версии норм с `source_url`, `verified_at`, пометки «требуют проверки» для годов вроде 2027+ (ADR-003 §4); без привязки к одной организации — **общий** справочник. |
| **P1b · Профиль с версиями и валидацией** | Сущности профиля по ADR-003, `effective_from`, правило первого числа месяца для налоговых полей, валидация несовместимых сочетаний; хранение по **организации** (арендатору). |
| **P2a · API чтения** | Выдача актуальной версии профиля и истории для UI/отчётов; учёт роли на чтение (без записи). |
| **P2b · API записи** | Создание новых версий профиля, роли **owner** / **accountant**, запись в **существующий** механизм аудита; запрет изменения снимка, уже применённого к **закрытому** периоду. |
| **P3 · Мастер в интерфейсе** | Шаги по §6 ADR-003; см. §9 этого плана (не блокирует отчёты). |
| **P4 · Качество расчётов и ОДДС** | Связка полей профиля с флагами качества и ОДДС; эквайринг — [ADR-002](ADR-002-acquiring-revenue-from-bank-statement.md). |
| **P5 · Персональный список выгрузок** | [FA-R03.2](FA-R03.2-export-checklist-by-profile.md) при изменении профиля. |

### 3.2 P1a — справочник норм

| Срез | Содержание |
| --- | --- |
| **Готовность** | Система отдаёт версию справочника для даты; записи с «требуют проверки» не выдаются без баннера/флага; административный или продуктовый контур знает, какая версия активна. |
| **Обязательные тесты** | Активная версия на границе года; согласованность полей справочника и ADR-003 §4.1; отсутствие утечки черновиков в пользовательские подсказки без пометки. |
| **Явно не входит** | Заполнение значений из внешних API ФНС в рантайме; автоматическая подстановка в профиль организации без решения пользователя. |

**Версия норм для 2025:** когда в продукте появятся **закрытые периоды 2025 года**, потребуется отдельная запись справочника (ориентир: ставка НДС **20%**, порог освобождения **60 млн** руб.). **До** её добавления `GET /tax-norms/current` с `as_of` **раньше 2026-01-01** возвращает **404** — это ожидаемое поведение P1a, не «дыра» в данных.

### 3.3 P1b — профиль с версиями и валидацией

| Срез | Содержание |
| --- | --- |
| **Готовность** | Для организации хранится цепочка версий с `effective_from`; валидация отклоняет заведомо несовместимые значения; применимый снимок к периоду определяется по правилам ADR-003. |
| **Обязательные тесты** | Переход `vat_status` и соседние поля; `effective_from` не ранее первого числа месяца для налоговых полей; миграция «одна стартовая версия» с `unknown`/`unspecified`. |
| **Явно не входит** | Полная перерасчётка закрытых периодов; дублирование журнала аудита вместо существующего механизма. |

### 3.4 P2a — API чтения

| Срез | Содержание |
| --- | --- |
| **Готовность** | Пользователь с допуском видит текущий профиль и при необходимости историю версий; отчётный слой может запросить снимок на дату для открытого периода. |
| **Обязательные тесты** | Доступ только в пределах **своей** организации (см. §6); отсутствие утечки профиля между арендаторами; кэш/ETag при необходимости — без нарушения актуальности. |
| **Явно не входит** | Массовая выгрузка профилей по всем организациям; публичные неаутентифицированные эндпоинты. |

### 3.5 P2b — API записи с ролями и аудитом

| Срез | Содержание |
| --- | --- |
| **Готовность** | **owner** / **accountant** создают новую версию профиля; события попадают в существующий аудит; попытка «править задним числом» закрытый период отклоняется. |
| **Обязательные тесты** | Запрет записи для viewer; двойная запись от двух ролей при разрешённой политике; идемпотентность или явные конфликты по версиям — по выбранной стратегии (фиксируется в задаче). |
| **Явно не входит** | Обход RBAC для «админки» без отдельного решения; удаление истории версий. |

---

## 4. Порядок и зависимости

1. **P1a** — справочник норм (общий контур для всех организаций).
2. **P1b** — модель профиля организации.
3. **P2a** — только чтение (можно параллельно с финализацией P1b при стабильном контракте).
4. **P2b** — запись и аудит после P2a и P1b.
5. **P3** — мастер после P2a/P2b.
6. **Вертикальный срез** (§8) — сразу после **P2** как приёмка модели.
7. **P4**, затем **P5** — по готовности контракта профиля и импорта.

**Критический путь:** P1a → P1b → P2a → P2b → вертикальный срез → P4.

---

## 5. Многоарендность

- **Профиль** принадлежит **организации** (в границах арендатора); данные одной организации **не доступны** другой на уровне API и в тестах изоляции.
- **Справочник норм** — **общий** (не копируется на каждую организацию); выбор версии норм применяется продуктом единообразно, профиль ссылается на применимые нормы через дату/версию по правилам продукта.

**Обязательный тест:** два тенанта с разными организациями — запрос профиля и событий аудита не пересекается; регресс при добавлении кэшей и фоновых задач.

---

## 6. Загрузка и жизненный цикл справочника норм

| Вопрос | Черновик политики |
| --- | --- |
| **Кто наполняет** | Команда продукта / назначенный **редактор справочника** (роль не совмещается с обычным пользователем организации без явного решения). |
| **Кто утверждает** | **Владелец продукта** или делегат (одно лицо на релиз версии норм). |
| **Когда проверять** | Перед **1 января** календарного года (граница порогов и дефляторов); **внепланово** при изменении НК/разъяснений ФНС, влияющих на записи справочника. |
| **Выпуск новой версии** | Новая запись версии с обновлёнными полями, `verified_at`, `source_url`; предыдущая версия остаётся для закрытых периодов; пользователям с «требуют проверки» — только с баннером до ручного подтверждения бухгалтером где применимо (см. ADR-003 §4.2). |

---

## 7. Миграции данных (только описательно)

- Ввести хранение **версий профиля** с `effective_from` и ссылкой на организацию/арендатора.
- Ввести **версии справочника норм** с метаданными проверки; связь с периодами отчётности — по политике продукта (не смешивать с версией профиля без явного правила).
- Для существующих организаций: одна **начальная версия** профиля с консервативными `unknown` / `unspecified` и баннерами (как в ADR-003); до **подтверждения** профиля — §2 этого плана.
- Закрытые периоды: применяется **снимок профиля на дату закрытия**; миграции не пересчитывают агрегаты задним числом.

Детали полей и ограничений — в миграционной задаче после утверждения схемы владельцем.

---

## 8. Вертикальный срез после P2 (приёмка модели)

После **P2** (read + write с аудитом):

1. В **подтверждённом** профиле меняют **статус НДС** (`vat_status`) на значение, при котором снимается неопределённость базы НДС.
2. На **одном существующем** экране (выбранном заранее в задаче приёмки) наблюдают изменение флага **`vat_basis_unknown`** (или эквивалента качества по ADR-003) в соответствии с новым значением.

Это считается **этапом приёмки модели** профиля до масштабного P4.

---

## 9. Мастер (P3)

- **Не блокирует** доступ к отчётам и основным экранам: комбинация **баннера** и ограничений **только налогово-зависимых** разрезов после подтверждения профиля (согласовано с §2).
- **ИНН:** проверка **формата** и **контрольной суммы** (алгоритм для ЮЛ/ИП — в задаче), **без** обращений к внешним API и без обогащения из ФНС в этом объёме.

---

## 10. Тесты (ожидаемый контур)

| Уровень | Фокус |
| --- | --- |
| **Контракт** | Валидность переходов `vat_status`, несовместимость режимов, дата `effective_from` для налоговых полей (P1b). |
| **API** | P2a/P2b: права ролей, изоляция арендаторов (§5), запрет подмены закрытого периода, аудит. |
| **Интеграционные (продукт)** | Вертикальный срез §8; мастер не блокирует навигацию; баннер при неподтверждённом профиле (§2). |
| **Справочник норм** | P1a: граница года, пометка «требуют проверки» (§6). |
| **Регресс расчётов** | После подтверждения профиля — флаги качества только для открытых периодов при смене версии; сценарии без ПДн. |

Объём e2e минимизировать: покрывать сценарии, где меняется поведение пользователя или отчёта.

---

## 11. Ориентир по объёму

Черновая оценка (после уточнения минимума полей §12 и ADR-003 §11):

- **P1a + P1b + P2a + P2b:** основная доля (модель, API, права, аудит).
- **Вертикальный срез §8:** небольшой инкремент, но обязателен как веха.
- **P3:** средний объём (UX, ИНН локально, баннеры).
- **P4:** высокая вариативность (сколько отчётов в первой волне).
- **P5:** средний объём при стабильном FA-R03.2.

Точные спринты не фиксируются в этом документе.

---

## 12. Решения, которые должен принять владелец

Базовый список — §11 [ADR-003](ADR-003-organization-profile-and-tax-rules.md). **Рекомендации редакции** к этому плану:

1. **Пилот (§2):** зафиксировать, что до подтверждения профиля **не** поднимать `unavailable` по налоговым разрезам из-за профиля — иначе ломается текущий пилот; баннер — да.
2. **Дробление P1/P2:** принять поэтапную поставку P1a→P1b→P2a→P2b или скорректировать границы между пакетами, если команда хочет объединить только read-path.
3. **Тестовая организация владельца:** после P2 сразу заполнять профиль — закрепить в релизных критериях.
4. **Изоляция (§5):** сделать блокирующим тестом на каждый релиз, где трогается профиль или кэш.
5. **Справочник норм (§6):** назначить редактора и регламент (раз в год + внепланово); не выпускать «жёсткие» подсказки без `verified_at`.
6. **Вертикальный срез (§8):** выбрать **один** экран-носитель для демонстрации `vat_basis_unknown` до разрастания P4.
7. **Мастер (§9):** подтвердить политику «отчёты открыты» и отсутствие внешних запросов по ИНН в v1.
8. **Граница P4:** какие отчёты первой волны переводятся на профиль после приёмки §8.
