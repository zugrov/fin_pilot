# FA-R03.2 · сверка банка с карточкой 51 (design)

**Статус:** design-only (2026-11-03). **Без записи в ledger и без product API** до отдельной приёмки.

## Граница этапа

- Сверка **S1 (ClientBank) ↔ S2 (карточка 51)** и контроль **S3/S13** ведётся под **FA-R03.2** как **read-only**:
  - локальный CLI `python -m app.tools.fa_r03_check` и чистые функции `reconcile.py`;
  - **не** вызывает `import_service`, **не** пишет в `cash_transactions`, **не** меняет `DatasetCoverage`.
- **FA-R03.3** — provenance, API и (при необходимости) сохранение **производных** отчётов сверки, не сырых выгрузок.
- **FA-R06.4** — закрытие периода (`closed`) и связь с отчётностью; не смешивать с MVP сверки.

## Два разных «reconciliation» (имена)

| Термин в продукте | Смысл | Статусы (FA-R02.4) |
|-------------------|--------|---------------------|
| **Полнота загрузки** | «Доставка cash за период полная и проверена» | `claimed` → owner **`reconciled`** на `DatasetCoverage` |
| **Согласование с 1С** | «Банковские документы сопоставлены с карточкой 51 и контрольными итогами» | `matched` / `exceptions` / **`owner_confirmed`** (отчёт FA-R03.2, v1) |

Одна кнопка «сверено» **не** должна одновременно закрывать полноту импорта и согласование с 1С без явного UX.

## Источники (приоритет решения A)

1. **S1** — первичный денежный поток.
2. **S2** — учётная детализация (корр. счета, 1→N строк).
3. **S3 / S13** — контроль итогов и дневных оборотов по 51 (допуск **0,00**).
4. **Ledger продукта** — отдельный шаг (см. ниже); не входит в MVP FA-R03.2.

## Ступени сопоставления S1 ↔ S2

Применяются **последовательно**; пул агрегатов карточки уменьшается по мере привязки.

| Ступень | Правило | Результат |
|---------|---------|-----------|
| **1** | Номер документа 1С **внутри названия** + **`business_date`** + **направление** + **сумма** (0,00) | одна пара → **matched**; 0 → ступень 2; >1 → **1b** |
| **1b** | Среди кандидатов ступени 1: все с одной **секцией ОДДС** (эталон по корр. счёту) | **равнозначные** → **matched** (авто); иначе **ambiguous** → **owner_confirmed** |
| **2** | **FIFO** по ключу `(direction, business_date, amount)` среди оставшихся агрегатов | **matched** или **not_found** |
| **—** | **Значимые ambiguous** (разные секции) | **не** в ступени 2; только **owner_confirmed** |

Агрегация карточки: строки с одним `(direction, business_date, document)` → один документ (сумма строк); см. `aggregate_card` / `aggregate_card_rows`.

Контроль до построчной сверки:

- формула остатка и **цепочка суток** S1;
- **S1 = S2 = S3** по счёту 51;
- опционально **S13 ↔ S1** по дням.

## Статусы отчёта согласования с 1С (v1)

| Статус | Условие |
|--------|---------|
| **preliminary** | импорт или файлы неполные; или разрыв цепочки / S1≠S2≠S3 |
| **matched** | контрольные итоги и цепочка OK; все S1 сопоставлены (ступени 1+2); **ambiguous = 0** |
| **exceptions** | есть **not_found**, **ambiguous** или расхождение контрольных итогов |
| **owner_confirmed** | владелец подтвердил разбор **ambiguous** / спорных пар (audit, без изменения ledger) |

## MVP (FA-R03.2, без БД)

В scope MVP:

- контрольные итоги **51** и **цепочка остатков** S1;
- матрица ступеней 1+2 и списки **not_found** / **ambiguous** (без ПII в stdout);
- пары **S1 ↔ S2** в памяти CLI.

Вне scope MVP:

- запись результатов в Postgres;
- сопоставление с **ledger** (`cash_transactions`) — отдельный подпакет **FA-R03.2d** или **FA-R03.3**;
- UI и `POST` reconcile.

## Ledger (отдельный шаг)

Сравнение committed cash в продукте с S1/S2:

- ключи: `external_id`, `(direction, business_date, amount)`, при необходимости fingerprint import;
- расхождения **ledger vs S1** и **ledger vs S2** — разные строки отчёта;
- не блокирует приёмку 2b/2c, пока импорт ClientBank не является единственным источником месяца на demo-БД.

## Хранение (после MVP)

- **Не** хранить сырые `.txt`/`.xls` клиента в git и на staging.
- Допустимо в v1: JSON-отчёт **производных** метрик (counts, sums, deltas, id пар без текстов) в `var/` или в `DatasetCoverage.evidence` после FA-R03.3 — по отдельному решению.

### Расхождение staged vs «направление + дата + сумма» (август)

| Проверка | Результат |
|----------|-----------|
| Независимое сопоставление (`match_aggregates`) | **218 / 218** |
| Staged (номер без даты → FIFO) | **1 not_found** после FIFO |

**Единственный not_found после staged:**

| Поле | Значение |
|------|----------|
| Дата | **2026-08-17** |
| Направление | **in** |
| Сумма | **1 080,00** |
| Корр. счёт (карточка) | **62.01** |
| Секция ОДДС (эталон) | **operating** |

**Почему не сопоставился в staged, а в независимом — да:**

1. **Ошибка алгоритма ступени 1 (не FIFO):** в CLI `match_by_document_number` номер ищется в названии документа карточки **без обязательного совпадения `business_date`**. Один и тот же номер встречается в названиях **разных** дат.
2. При **последовательном** проходе S1 документ **2026-08-03 in 1 080,00** (статически **7** кандидатов, **ambiguous**) после «съедания» пула другими совпадениями остаётся **один** кандидат в pool — агрегат карточки с датой **2026-08-17** и корр. **62.01**. Staged ошибочно считает это **unique** match ступени 1 и **удаляет** агрегат из пула.
3. Законный S1 **2026-08-17 in 1 080,00** попадает в FIFO (номер не найден в оставшемся пуле). К **2026-08-17** агрегата уже нет → **not_found**.
4. Независимая проверка матчит по **`(direction, business_date, amount)`**, поэтому **08-03** не забирает агрегат **08-17** → **218/218**.

**Очередь FIFO «24 при not_found=23»:** не лишняя строка в данных, а **лишний** элемент FIFO из‑за пункта 2: документ, который по полному пулу **ambiguous**, после мутации pool попадает в FIFO как «не найден», хотя `match_by_document_number` считает его в счётчике **ambiguous** (6), а не **missing** (23).

**Исправление (до реализации в коде — только после «да» владельца):**

- Ступень **1**: добавить **`business_date`** к условию (как уже сделано в `reconcile.match_statement_to_card` по полному ключу с номером).
- **Не** снимать агрегат с пула при **ambiguous**; применять **1b** (авто только для **равнозначных**).
- Пересчитать staged-отчёт; ожидание: **0 not_found** при сохранении **218/218** независимой проверкой.
